# Промпт для Codex партнёра: финальная интеграция HackAlem AI

> Перед отправкой: изменения с ноутбука Нурали станут доступны партнёру только после `git push` в ветку `backend`.

Ты отвечаешь за финальную интеграцию проекта HackAlem AI для ekt.kz. Цель — один запускаемый проект, где открывается сайт-прототип магазина, а на его страницах работает плавающее окно ассистента. Отдельная страница ассистента допустима дополнительно. Корзина и чат должны использовать одну серверную сессию.

Сначала прочитай `AGENTS.md` и `docs/PROJECT_BRIEF.md` из свежей ветки `backend`, затем `docs/00_ПОЛНЫЙ_ПЛАН_HackAlem_ekt.md`, `docs/03_КОНТРАКТ_API.md`, документы обеих ролей, `docs/DESIGN_BRIEF.md`, `docs/BUYING_TERMS_SOURCES.md` и `docs/CATALOG_API_SHAPE.md`. Текущий запрос разрешает тебе выполнять интеграционные изменения и в `apps/web`, и в `apps/api`. Официальное ТЗ и пять обязательных сценариев держи в фокусе на каждом этапе.

1. Проверь `git status`, все локальные рабочие деревья и свежие `origin/main`, `origin/backend`, `origin/frontend` и `origin/mockup-web`. Сравни ветки и составь короткий план на ближайшие 45–60 минут, затем сразу выполняй его. Не считай, что изменения с другого ноутбука доступны, пока они не отправлены в GitHub: если `backend` отстаёт, назови последний видимый SHA и попроси Нурали сделать `push`. Сохрани все локальные незакоммиченные изменения. Не используй `reset`, `force push` или `git clean`.

2. В своей ветке `frontend` собери функциональность обеих сторон в один проект. Сохрани новые возможности backend, текущий чат и корзину frontend, а также полезный макет магазина и плавающий чат из `mockup-web`. Разрешай конфликты по смыслу, не теряя функций и тестов. Главная `/` должна показывать сайт-прототип с доступным на мобильном и десктопе помощником. Подключи настоящий клиент `/api/*`, а не только локальный mock. Сохрани видимую маркировку демо-данных: это пока не внедрение в боевой ekt.kz и не его настоящая корзина.

3. Пройди все пять сценариев из `docs/PROJECT_BRIEF.md` через браузер и API: товар и остаток, обоснованный аналог, условия покупки с источником, предложение без изменения корзины, отдельное подтверждение с повторной проверкой остатка и ссылка на актуальную `/cart`. Проверь двойной клик, обновление страницы, разные сессии, ошибки сети, ширину 360 px, файлы и казахский интерфейс там, где они заявлены. Добавь регрессионные проверки для «Не добавляй», «Отмена» во время ожидания каталога, «Добавь два», отрицательного/дробного количества и нескольких артикулов. Нельзя молча менять количество или терять позицию.

4. Используй доступные ресурсы максимально эффективно: параллельные независимые проверки, инструменты и агентов, если они доступны; затем лично проверь общий результат. Не останавливайся после плана или успешной сборки одной части. Исправляй найденные проблемы и повторяй проверку. Для внешнего ИИ и каталога соблюдай разрешения из `AGENTS.md`: никаких секретов в выводе, данных партнёра во внешней модели без разрешения и нагрузочных тестов инфраструктуры.

5. Убери только доказанно устаревшие дубликаты, неиспользуемый код и случайные артефакты. Не удаляй чужие локальные файлы, `.env`, приватный индекс каталога или незакоммиченную работу. Приведи структуру и команды запуска к понятному виду, желательно с едиными командами из корня.

6. Сделай полностью актуальный `README.md` для человека, который впервые открыл чистый клон: что реализовано и что ещё ограничено; архитектура web/API/каталога/ИИ/корзины; требования и установка; настройка `.env.example` без секретов; точные команды запуска и сборки; демо-артикулы и пошаговый сценарий; режимы demo/live; загрузка файлов; тесты; частые ошибки; безопасность и ограничения интеграции с ekt.kz. Проверь каждую команду README из чистого клона. Не называй неподключённую функцию готовой.

Перед коммитом просмотри diff и проверь отсутствие секретов. Сделай содержательные коммиты и `push` в `frontend`. Итогом дай SHA, список объединённых возможностей, результаты тестов и браузерного сценария, оставшиеся ограничения. Подготовь объединённую ветку для проверки Нурали и слияния в `main`; не объявляй проект «100% готовым», пока обе части вместе не запускаются по README и пять обязательных сценариев не проходят.
