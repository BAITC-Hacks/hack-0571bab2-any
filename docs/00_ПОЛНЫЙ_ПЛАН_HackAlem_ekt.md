# HackAlem AI — план команды для кейса ekt.kz

Версия: 23.09.2026. Команда: backend — Нурали, frontend — напарник. Рабочее окно хакатона — 5 часов после официального старта.

## 1. Что уже известно и что ещё надо подтвердить

**Подтверждено документами:** выбранный кейс — ИИ-ассистент для чата ekt.kz. В обязательной части нужны: (1) достоверные наличие, характеристики и сертификат из каталога; (2) минимум один обоснованный аналог для отсутствующего товара; (3) условия оплаты, доставки и минимальной партии; (4) изменение корзины только после явного согласия клиента и в пределах остатка; (5) ссылка на актуальную корзину. Пользователь может писать свободным текстом и прикладывать Excel, Word, PDF, JPEG или фото. Интерфейс должен работать на мобильном и десктопе. На разработку дано 5 часов; финальный код нужен в репозитории команды, выданном платформой, с README и отправкой на странице треков.

**Дано партнёром:** описание кейса и отдельный документ с доступом к API каталога. Доступ хранить только в локальном хранилище секретов или переменных окружения backend. Не переписывать логин и пароль в промпты, задачи, Git, логи, скриншоты и эти файлы. Каталог читать только в разрешённом объёме; не делать массовую выгрузку без необходимости.

**Не найдено в предоставленных материалах:** точная схема ответов API, API корзины ekt.kz, подтверждённые условия оплаты/доставки/минимальной партии, критерии и веса оценивания, готовый тестовый контур сайта, разрешение на передачу данных партнёра внешним моделям. Эти пункты уточнить у ментора/партнёра в первые 20 минут. Если ответов нет, показать прототип на синтетических данных и честно обозначить ограничения. Не заявлять, что тестовая корзина интегрирована с реальным ekt.kz.

**Отдельная инструкция ASU:** онлайн-курс Entrepreneurship Foundations и цифровой бейдж. В приложенных правилах он не назван условием зачёта или оценивания этого кейса. Проходить отдельно от пятичасового окна, если организаторы не скажут иначе.

## 2. Как выглядит сильная сдача

Жюри за 2–3 минуты видит работающий путь: товар по артикулу → наличие, характеристики, сертификат при наличии → товар с нулевым остатком → подходящий аналог с объяснением → вопрос об условиях покупки → предложение положить 2 штуки → корзина **не меняется** до нажатия «Подтвердить и добавить» или однозначного «Да, добавь» → остаток проверяется ещё раз → открывается ссылка на корзину с двумя штуками. Все числа и ссылки берутся из текущих данных, а отсутствие сведений честно показано.

Главная цель — закрыть все пять обязательных проверок устойчиво, затем сделать быстрый, аккуратный и понятный интерфейс. Первое место нельзя гарантировать: веса оценивания и решения других команд неизвестны.

**Репетиция перед жюри, 90 секунд:** открыть чат на телефоне или узком окне; спросить о синтетическом артикуле с наличием и показать характеристики/сертификат; спросить об отсутствующей позиции и показать обоснованный аналог; спросить условия покупки и показать подтверждённый источник либо честное ограничение; попросить две штуки и сначала показать пустую корзину; явно подтвердить и открыть ссылку на корзину с двумя штуками. Отдельно приготовьте резервную запись этого сценария на синтетических данных на случай сбоя сети. Не обещайте скорость «в секунды» до измерения: целевой отклик — единицы секунд по кейсу, замерьте 10 запросов и укажите фактический результат.

## 3. Рекомендуемая архитектура

```text
Клиент → React/Vite web → /api backend → адаптер каталога ekt.kz (только чтение)
                         ↘ локальный демонстрационный каталог, если live API недоступен
                         ↘ OpenAI API для понимания запроса и формулировки ответа
                         ↘ сессия, ожидаемое подтверждение, демонстрационная корзина
```

- Один репозиторий команды. `apps/web` — frontend, `apps/api` — backend, `packages/contracts` — общие типы/схемы, `docs` — контракт и доказательства проверки. Инструменты: TypeScript, React/Vite, Node.js/Fastify, Zod; npm workspaces. Если подготовленный репозиторий уже имеет стек, **сохраняйте его** и адаптируйте роли к существующей структуре.
- Секреты и запросы к каталогу — только на сервере. Браузер не получает Basic Auth и ключи моделей. Каталог привести к единой внутренней модели `Product`; не связывать UI с непроверенной схемой ekt API.
- ИИ распознаёт намерение, извлекает артикул/количество и помогает формулировать ответ. Поиск товара, факт наличия, цена, сертификат, выбор аналогов и изменение корзины проверяются кодом на сервере. Модель не является источником товарных фактов и не получает права напрямую записывать корзину.
- Для аналогов: сначала та же категория и назначение, затем совместимые критичные параметры, затем доступный остаток. Показать совпавшие характеристики и причину. При отсутствии проверенного аналога так и сказать; не подменять технически важные товары случайными похожими названиями.
- Сертификат показывать только если он есть в данных и ссылка валидна. Условия покупки хранить как подтверждённые данные партнёра с датой источника; если их нет, ответить «Нужны подтверждённые условия от менеджера» и предложить обращение. Никаких выдуманных сроков и минимальной партии.
- Корзина привязана к сессии. Сообщение в чате создаёт только `proposalId` с товарами и количеством. Отдельный `confirm` после явного действия клиента перечитывает остаток, проверяет предел, предотвращает повторное добавление и выдаёт путь `/cart` к состоянию этой же сессии. Без API корзины ekt.kz это **корзина прототипа**. Для реальной интеграции нужен разрешённый контракт сайта и его авторизация.
- Загрузка файлов — отдельный этап после обязательного текстового потока. Ограничить размер и тип, извлекать только нужные позиции, не выполнять макросы и не отправлять вложения сторонним сервисам без разрешения. Для JPEG/фото использовать распознавание только при разрешённой передаче данных; всегда давать пользователю проверить распознанный артикул.

Точный контракт согласован в [03_КОНТРАКТ_API.md](03_КОНТРАКТ_API.md). Оба исполнителя работают по нему.

## 4. До старта

1. У каждого — рабочие ноутбук/зарядка, Git, Node.js, браузер, Codex; при необходимости проверенный переходник Ethernet и DHCP. Войти в аккаунты заранее.
2. Активировать Pro/Codex и кредиты **личными ссылками** из платформы. Проверить в интерфейсах факт начисления и срок действия; $50 OpenAI API и $50 NVIDIA не считать одним общим кошельком. Включить уведомления/лимит расходов на проекте API. Ключи создать с коротким сроком действия и не показывать друг другу в чате.
3. Убедиться, что оба имеют доступ к **одному репозиторию команды**, выданному платформой. Настроить ветки `backend` и `frontend` или небольшие PR; договориться, кто вносит контракт. Не публиковать код кейса или данные партнёра в личном публичном репозитории.
4. Подготовить 5–8 **синтетических** товаров для демонстрации: товар в наличии с сертификатом, отсутствующий с проверенным аналогом, товар с малым остатком, позиция без сертификата. Зафиксировать ожидаемые результаты.
5. Подготовить короткий список вопросов партнёру: схема каталога и пагинации, частота обновления остатков, разрешённые данные для внешнего ИИ, источник условий покупки, API корзины/тестовый сайт, целевые критерии жюри.

## 6. Работа вдвоём в Codex

1. Открыть репозиторий команды в двух Codex на собственных компьютерах и аккаунтах. Backend читает [01_ЗАДАНИЕ_BACKEND_Codex.md](01_ЗАДАНИЕ_BACKEND_Codex.md), frontend — [02_ЗАДАНИЕ_FRONTEND_Codex.md](02_ЗАДАНИЕ_FRONTEND_Codex.md). В обоих файлах одинаковая общая постановка и один API-контракт, но разные границы работы.
2. Создать общий документ API/схемы в первые 20 минут; любое изменение сразу сообщать партнёру. Никто не меняет чужую часть без сообщения. Мержить маленькими порциями каждые 30–45 минут.
3. Каждый запрос Codex формулировать как небольшой проверяемый результат: «сделай поиск по артикулу и тест с одним товаром», «сделай кнопку явного подтверждения и проверь, что до неё нет POST confirm». После результата просматривать diff и запускать соответствующую проверку.
4. При несовпадении схемы live API сохранять UI-контракт и исправлять адаптер backend. При недоступности модели показывать безопасный ответ на шаблонах, а не ломать чат. Не тратить первые часы на смену стека, агентный фреймворк, векторную БД или несколько моделей.
5. Отдельные ветки/PR и коммиты показывают личный вклад. В конце один участник проверяет общий запуск с чистого клона, второй идёт по демонстрационному сценарию.

## 7. Кредиты, модели и плагины

- **Codex Pro 5x** использовать для разработки и ревью кода. Это подписка на инструмент разработки; не считать её оплатой вызовов OpenAI API в приложении. Фактические лимиты и баланс проверять в своих кабинетах.
- **OpenAI API $50** — основной вариант для понимания запросов. Один доступный в аккаунте быстрый текстовый/мультимодальный вариант выбрать после измерения скорости и стоимости на 10 синтетических запросах. Использовать Responses API/функции или строгий JSON для извлечения намерения, с серверной проверкой всех действий. Для документов сначала локально извлекать текст и отправлять только разрешённый фрагмент. Официальные руководства: [function calling](https://developers.openai.com/api/docs/guides/function-calling), [file inputs](https://developers.openai.com/api/docs/guides/file-inputs), [контроль расходов](https://developers.openai.com/api/docs/guides/spend-limits).
- **NVIDIA $50** держать как запасной вариант для inference или распознавания, если выбранный сервис и модель подтверждены доступными в аккаунте. Brev-кредиты и Build/API-токены могут иметь разные назначения; проверить кабинет и правила промо до интеграции. Не строить вторую ветку моделей, пока первая не закрыла обязательный сценарий. [Официальный NVIDIA API quickstart](https://docs.api.nvidia.com/nim/docs/api-quickstart).
- **OpenAI Developers** (подключение проектного API-ключа и документация) и **Codex Security** (проверка кода перед сдачей) теперь установлены; статус обоих проверен в каталоге плагинов 23.09.2026. Наличие плагинов не подтверждает активацию промокодов, создание API-ключа или готовность приложения: это проверить отдельно. GitHub уже доступен как инструмент Codex, дополнительные Figma/Linear/Notion для пятичасового кейса не обязательны. Любому плагину давать доступ к коду/данным партнёра только в рамках разрешения организаторов.

## 8. Приёмочные проверки

| ID | Запрос/действие | Ожидается |
|---|---|---|
| T1 | Существующий артикул | Точное название, остаток/статус, ключевые характеристики; сертификат только если есть в каталоге |
| T2 | Артикул с нулевым остатком | Минимум один совместимый и доступный аналог с причиной; при отсутствии проверенного аналога — честный отказ |
| T3 | «Какая оплата, доставка и минимальная партия?» | Только подтверждённые условия; при отсутствии данных — явное «не известно»/передача менеджеру |
| T4 | «Добавь 2 штуки» без дальнейшего согласия | Предложение с количеством; корзина не изменилась |
| T5 | Явное «Да, добавь» или кнопка подтверждения | Повторная проверка остатка, одно добавление, актуальная корзина, работающая ссылка `/cart` |
| T6 | Запрос больше остатка | Добавление блокируется или предлагается доступное количество для нового подтверждения |
| T7 | Повторный `confirm`/обновление страницы | Нет двойного добавления |
| T8 | API каталога или модель недоступны | Понятная ошибка/безопасный fallback; никаких выдуманных цен и остатков |
| T9 | Мобильный экран и вложение | Чат читаем; вложение, если реализовано, явно показывает извлечённые позиции для проверки |

Сохранить короткую запись экрана или скриншоты T1–T5 на синтетических данных без ключей и личной информации. Если время мало, T1–T8 важнее бонусов.
