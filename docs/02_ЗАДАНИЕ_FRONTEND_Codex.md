# HackAlem AI ekt.kz — задание для Codex: frontend

Версия 1 · 23.09.2026 · Ответственный: напарник

## Общая постановка для обоих участников

За 5 часов создать в одном репозитории команды работающий прототип ИИ-чата для ekt.kz. Обязательные проверки: (1) товар по артикулу с достоверным наличием, характеристиками и сертификатом при его наличии; (2) аналог отсутствующего товара с причиной; (3) подтверждённые условия оплаты, доставки и минимальной партии; (4) добавление в корзину только после явного согласия и в пределах остатка; (5) прямая ссылка на актуальную корзину. Десктоп и мобильный интерфейсы обязательны. Пользовательские вложения Excel, Word, PDF и JPEG предусмотрены кейсом, но реализуются после стабильного текстового сценария.

Факты о товаре и условия покупки нельзя выдумывать. Партнёрский каталог доступен через отдельный документ с Basic Auth; учётные данные остаются только на backend и никогда не попадают в Git, промпты, логи или браузер. API корзины ekt.kz в материалах отсутствует; до получения его от партнёра делаем явно обозначенную корзину прототипа и не заявляем интеграцию с боевым сайтом. Публичная страница ekt.kz даёт способы оплаты/доставки, но пороги на сайте расходятся, а минимальная партия не указана: см. `docs/BUYING_TERMS_SOURCES.md`. Работать только в официальной сети мероприятия и с разрешёнными данными.

Оба участника используют один контракт: [03_КОНТРАКТ_API.md](03_КОНТРАКТ_API.md). Любое изменение контракта немедленно согласовывать. Личный вклад каждого должен быть виден в коммитах. README описывает только реально реализованное. Официальные критерии и время сдачи уточнить после старта.

## Твоя зона: frontend

Ты владеешь `apps/web`, компонентами чата, карточками товаров, подтверждением и экраном корзины. Ты не меняешь `apps/api` без согласования. В первые 20 минут согласуй с backend поля ответа и примеры JSON. Следуй `docs/DESIGN_BRIEF.md`. Если в выданном репозитории уже есть структура, работай в ней; не меняй стек без причины.

### Порядок реализации

1. **Скелет.** React/Vite + TypeScript, один экран чата с ясным заголовком, полем ввода, отправкой по Enter и кнопке. Мобильная ширина 360 px и десктоп. Разумные контрасты, фокус, подписи, состояние загрузки и понятные ошибки. Никаких ключей в браузерном коде.
2. **Товар.** Карточка с артикулом, названием, остатком/статусом, ключевыми характеристиками, сертификатом только по подтверждённому URL и ценой только если API её дал. Видимая метка «Демо-данные», если `factsSource=catalog_demo`. Не показывать неизвестное как ноль.
3. **Аналоги.** Отдельный блок с объяснением `reason`, сравнимыми характеристиками и кнопкой выбрать вариант. Не скрывать ограничений и различий, которые могут повлиять на совместимость.
4. **Условия покупки.** Отображать только ответ backend и его статус источника. При отсутствии подтверждённых правил — сообщение «Уточните у менеджера»; не писать фиктивные цены, сроки или минимальную партию.
5. **Подтверждение.** Полученный `proposal` показать как проверяемый список товаров/количеств. **Не вызывать `POST /api/cart/confirm` автоматически** после сообщения пользователя «хочу», выбора товара, открытия карточки или появления proposal. Кнопка «Подтвердить и добавить» вызывает confirm один раз и блокируется до ответа. При ошибке остатка предложить новое количество и новое подтверждение. После успеха показать ссылку `/cart` и актуальное содержимое корзины.
6. **Корзина.** Отдельная страница `/cart`, читает `GET /api/cart` той же сессии; при пустой корзине честное пустое состояние. Ссылка после добавления ведёт туда. Не делать вид, что это реальная корзина ekt.kz, пока backend не подтвердит интеграцию.
7. **Вложения после T1–T8.** Drag/drop или кнопка выбора для PDF/DOCX/XLSX/JPEG, предпросмотр имени/размера, прогресс/ошибка, показ распознанных артикулов с ручным подтверждением. Вложение само не добавляет товары.

### Минимальные проверки интерфейса

- Карточка товара показывает факты из JSON и скрывает отсутствующий сертификат.
- Нулевой остаток и аналог ясно различаются, причина видна.
- До явного подтверждения не было запроса `confirm` и корзина не изменилась.
- После подтверждения ссылка `/cart` открывает ту же корзину; двойной клик не удваивает товар.
- Ошибка API и отсутствие сети понятны пользователю; на узком экране чат, карточки и кнопка подтверждения доступны.

## Стыки с backend

До 20-й минуты: согласовать `Product`, `Analog`, `/api/chat`, `/api/cart/confirm`, `/api/cart`, ошибки и cookie. До 90-й минуты: подключить работающий `POST /api/chat` на `catalog_demo`. До 150-й: подключить подтверждение/корзину. При несовпадении live API фронт не переписывать, попросить backend исправить адаптер. В финале вместе пройти T1–T8 из полного плана.

## Готовый первый запрос твоему Codex

> Прочитай полный план и единый API-контракт команды. Ты отвечаешь только за frontend. Сначала осмотри выданный репозиторий и предложи краткий план на первые 90 минут с конкретными файлами, затем реализуй мобильный и десктопный экран чата, карточку товара/аналога и клиент для `/api/chat` по контракту. Для начала используй безопасный mock JSON без реальных данных партнёра и без секретов. Не меняй backend. После изменений покажи diff, проверь сборку и назови следующий шаг по контракту.

Следующие запросы давать небольшими задачами: (а) блок условий; (б) видимый pending proposal; (в) ручной confirm; (г) `/cart`; (д) мобильная полировка; (е) вложения при оставшемся времени. Каждый раз проверять фактический результат.

## Готовность к сдаче

- Все пять обязательных сценариев проходят с backend; где партнёрские данные недоступны, демонстрационный режим явно виден.
- Web собирается с чистого клона, работает на мобильной и десктопной ширине, без секретов в bundle.
- Подтверждение действительно ручное, двойной клик не создаёт лишних изменений, ошибки и пустые состояния понятны.
- Коммиты frontend отражают личный вклад напарника, ветка объединена с общей до сдачи.
