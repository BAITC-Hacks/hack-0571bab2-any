# Единый контракт backend ↔ frontend

Версия 1. Согласовать в первые 20 минут после старта. Если репозиторий команды уже содержит контракт, этот документ использовать как список требований и адаптировать к нему.

## Принципы

- Все пути ниже относятся к **нашему прототипу**, а не к API ekt.kz. Только backend знает формат и учётные данные партнёрского API.
- JSON в UTF-8, денежные значения передавать строкой/целым числом в минимальных единицах с валютой, никогда не рассчитывать цену в модели. Поля, которых нет у партнёра, возвращать `null`, без догадок.
- Корзина изолирована по серверной сессии. Браузер получает безопасный cookie `HttpOnly; SameSite=Lax; Secure` на HTTPS. Изменение состояния — только POST с проверкой origin и CSRF-токена. В запросах/URL не передавать API-ключи или Basic Auth.
- Источник фактов — `catalog_live`, `catalog_demo`, `partner_policy` или `unknown`. UI видимо помечает демонстрационные данные. `cartUrl` — `/cart` внутри прототипа, пока не подтверждена интеграция с ekt.kz.

## Модель данных

```ts
type Product = {
  id: string; sku: string; name: string; category?: string | null;
  characteristics: Record<string, string>;
  certificateUrl?: string | null;
  price?: { amount: string; currency: string } | null;
  stock: { available: number | null; status: 'in_stock' | 'out_of_stock' | 'unknown' };
  source: 'catalog_live' | 'catalog_demo';
};

type Analog = { product: Product; reason: string; matchedCharacteristics: string[] };
type CartItem = { productId: string; sku: string; name: string; quantity: number; availableAtConfirmation: number | null };
type ApiError = { error: { code: string; message: string; requestId?: string } };
```

`stock.available = null` означает неизвестный остаток: подтверждение добавления блокируется до проверки. Сертификат показывать только при существующем и проверенном URL. Не отображать неизвестную цену как ноль.

## Эндпоинты

### `GET /api/health`

`200 {"ok":true,"catalog":"live|demo|unavailable","model":"ready|fallback"}`. Без деталей конфигурации и секретов.

### `POST /api/chat`

Запрос: `{"message":"Есть ли артикул ABC-123?","locale":"ru"}`. `locale` — `ru` или `kk`, если казахский реализован. Сессия определяется cookie. Ответ:

```json
{
  "reply": "Товар ABC-123 есть в наличии: 4 шт. ...",
  "products": [],
  "analogs": [],
  "proposal": null,
  "factsSource": "catalog_demo",
  "cartChanged": false,
  "requestId": "req_demo_1"
}
```

Для намерения «добавь 2» сервер возвращает `proposal: {"id":"...","items":[{"productId":"...","quantity":2}],"expiresAt":"..."}`; `cartChanged` остаётся `false`. Если текст **однозначно подтверждает уже выданное предложение**, сервер может обработать его через тот же внутренний механизм подтверждения, что и кнопка, и вернуть `cartChanged: true`, `cart: {...}` и `cartUrl: "/cart"`. Никакого добавления по первому намерению «хочу/покажи/в корзину?» без отдельного подтверждения.

### `POST /api/cart/confirm`

Запрос: `{"proposalId":"...","idempotencyKey":"..."}` после нажатия пользователем явной кнопки. Сервер проверяет сессию, срок и содержимое предложения, заново читает остаток, ограничивает количество, проверяет повтор ключа и только затем меняет корзину. Ответ:

```json
{
  "cart": {"items": [{"productId": "demo-1", "sku": "ABC-123", "name": "Демо-товар", "quantity": 2, "availableAtConfirmation": 4}], "itemCount": 2},
  "cartUrl": "/cart",
  "status": "added",
  "requestId": "req_demo_2"
}
```

При превышении остатка — `409` с `code: "INSUFFICIENT_STOCK"` и доступным количеством в безопасном поле `available`; клиент должен предложить новое подтверждение. При повторе того же `idempotencyKey` вернуть прежний результат без второго добавления. При истечении срока предложения — `409 PROPOSAL_EXPIRED`.

### `GET /api/cart`

Текущая корзина **этой** сессии: `{"items":[...],"itemCount":2,"cartUrl":"/cart","mode":"demo"}`. В реальный ekt.kz режим переходить только после получения партнёрского API корзины и тестового разрешения.

### `POST /api/attachments` — после обязательного сценария

`multipart/form-data`, один файл: PDF/DOCX/XLSX/JPEG, лимит размера и количества страниц/строк. Возвращает только кандидаты артикулов/количеств `[{"sku":"...","quantity":2,"confidence":"low|medium|high"}]` и предупреждение о необходимости проверки. Никаких изменений корзины. Неподдерживаемый файл — `415`, слишком большой — `413`.

## Правила ошибок и fallback

- `400` невалидный ввод, `401/403` проблема доступа к данным на сервере без раскрытия деталей, `404` товар не найден, `409` конфликт остатка/подтверждения, `429` лимит, `503` каталог/модель временно недоступны.
- Если модель недоступна, поиск по артикулу и шаблонный ответ продолжают работать. Если каталог недоступен, ответ по остаткам/цене запрещён; в демо можно переключиться на явно обозначенный синтетический набор.
- Таймаут внешнего запроса, ограниченные повторы и короткая понятная ошибка в чате. Не включать пароль, ключ, полный запрос клиента, содержимое файла или Basic Auth в логи. Допустимы `requestId`, код ошибки, длительность и режим данных.

## Блокирующие вопросы партнёру

1. Есть ли тестовый API корзины и механизм связи с авторизованной сессией ekt.kz?
2. Где подтверждение спорного порога бесплатной доставки и минимальной партии? Публичный источник оплаты/доставки и его ограничения приведены в `docs/BUYING_TERMS_SOURCES.md`.
3. Какие поля/единицы есть в ответах каталога, как искать по артикулу, где сертификаты и остатки?
4. Разрешена ли передача товарных и пользовательских данных в OpenAI/NVIDIA API для этого кейса?
5. Нужны ли особые требования к фотографиям и документам в оценивании?

Пока на вопрос 1 нет ответа, прототип демонстрирует собственную корзину. Условия оплаты и общие условия доставки можно отвечать с ссылкой на публичную страницу; спорный порог и минимальную партию — только после подтверждения партнёра. Не выдавать это за полную интеграцию с сайтом.
