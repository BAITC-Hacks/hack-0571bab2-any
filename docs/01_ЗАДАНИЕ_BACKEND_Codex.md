# HackAlem AI ekt.kz — задание для Codex: backend

Версия 1 · 23.09.2026 · Ответственный: Нурали

## Общая постановка для обоих участников

За 5 часов создать в одном репозитории команды работающий прототип ИИ-чата для ekt.kz. Обязательные проверки: (1) товар по артикулу с достоверным наличием, характеристиками и сертификатом при его наличии; (2) аналог отсутствующего товара с причиной; (3) подтверждённые условия оплаты, доставки и минимальной партии; (4) добавление в корзину только после явного согласия и в пределах остатка; (5) прямая ссылка на актуальную корзину. Десктоп и мобильный интерфейсы обязательны. Пользовательские вложения Excel, Word, PDF и JPEG предусмотрены кейсом, но реализуются после стабильного текстового сценария.

Факты о товаре и условия покупки нельзя выдумывать. Партнёрский каталог доступен через отдельный документ с Basic Auth; учётные данные остаются только на backend и никогда не попадают в Git, промпты, логи или браузер. API корзины ekt.kz и подтверждённые правила оплаты/доставки в материалах отсутствуют: до получения их от партнёра делаем явно обозначенную корзину прототипа и не заявляем интеграцию с боевым сайтом. Работать только в официальной сети мероприятия и с разрешёнными данными.

Оба участника используют один контракт: [03_КОНТРАКТ_API.md](03_КОНТРАКТ_API.md). Любое изменение контракта немедленно согласовывать. Личный вклад каждого должен быть виден в коммитах. README описывает только реально реализованное. Официальные критерии и время сдачи уточнить после старта.

## Твоя зона: backend

Ты владеешь `apps/api`, адаптером каталога, серверной сессией/корзиной и серверными тестами. Ты не меняешь верстку `apps/web` без согласования. В первые 20 минут согласуй с frontend поля ответа и примеры JSON. Если в выданном репозитории уже есть структура, работай в ней; не меняй стек без причины.

### Порядок реализации

1. **Скелет.** Node.js + TypeScript + Fastify, проверка env на старте, `GET /api/health`, ошибки с `requestId`. `.env.example` содержит имена переменных, пустые значения и пояснения; реальные значения хранить вне Git. Включить `.env*` в `.gitignore`, кроме `.env.example`.
2. **Каталог.** Определить фактическую схему API только разрешённым чтением и без вывода секретов в терминал/логи. Вынести `CatalogProvider` с `live` и `demo` реализациями, нормализовать поля в `Product`. Учесть пагинацию, пустой ответ, таймаут, `401`, `429`, нулевой и неизвестный остаток. Кэшировать кратко, но перед добавлением перечитывать остаток. Не выгружать весь каталог без нужды.
3. **Поиск и аналог.** Сначала точный артикул, затем осторожный поиск по названию. Аналог — только доступный товар с той же задачей/категорией и совместимыми критичными параметрами. Отдавать `reason` и совпавшие характеристики. Для опасной несовместимости — «проверенного аналога нет».
4. **Ответы.** Извлекать намерение/артикул/количество из запроса; модель — помощник для языка, а не источник цены или остатка. Не передавать партнёрские/личные данные внешней модели без разрешения. В демо использовать синтетические данные. Для условий покупки — подтверждённый источник с датой; пока его нет, честный fallback. Не включать платежные данные в схему.
5. **Подтверждение.** Первое намерение «добавь» создаёт ожидаемое предложение, но не мутирует корзину. Только отдельное явное «да, добавь» к актуальному предложению или кнопка `POST /api/cart/confirm` вызывает одну серверную функцию. Проверить сессию, срок, количество, текущий остаток и идемпотентность. Возвращать `/cart` этой же сессии. Защитить от дублирования и межсессионного доступа.
6. **Вложения после T1–T8.** PDF/DOCX/XLSX/JPEG принимать с лимитами; локально извлекать текст/таблицы. Фото — только если разрешён внешней модели и пользователь подтверждает результат распознавания. Возвращать кандидаты артикулов, не менять корзину.
7. **Операционность.** Разумные таймауты, безопасные ошибки, минимальные логи, ограничение запросов/размера тела, очистка временных файлов. Секреты не попадают в ответы, stack trace и commit history.

### Минимальные автоматические проверки

- Точный артикул возвращает поля из fixture; сертификат отсутствует, если его нет в fixture.
- Нулевой остаток даёт проверенный аналог и объяснение.
- Без подтверждения корзина пуста; после подтверждения ровно одно добавление и корректный `/cart`.
- Запрос количества выше остатка блокируется; повторный `confirm` не дублирует позицию.
- `401/таймаут` каталога не превращаются в выдуманные факты.

## Стыки с frontend

До 20-й минуты: согласовать `Product`, `Analog`, `/api/chat`, `/api/cart/confirm`, `/api/cart`, ошибки и cookie. До 90-й минуты: дать frontend работающий `POST /api/chat` на `catalog_demo`. До 150-й: дать подтверждение/корзину. После каждой смены схемы присылать пример ответа без секретов. В финале вместе пройти T1–T8 из полного плана.

## Готовый первый запрос твоему Codex

> Прочитай полный план и единый API-контракт команды. Ты отвечаешь только за backend. Сначала осмотри выданный репозиторий и предложи краткий план на первые 90 минут с конкретными файлами, затем реализуй минимальный API: health, демонстрационный каталог, поиск по артикулу и `/api/chat` с фактами из каталога. Не читай и не выводи реальные секреты; данные партнёра и чужой конфиденциальный код не передавай другим сервисам без разрешения. Не меняй frontend. После изменений покажи diff, запусти короткую проверку и назови следующий шаг по контракту.

Следующие запросы давать небольшими задачами: (а) аналоги; (б) условия без выдумки; (в) pending proposal; (г) confirm + идемпотентность; (д) обработка live API; (е) загрузки при оставшемся времени. Каждый раз проверять фактический результат.

## Готовность к сдаче

- Все пять обязательных сценариев проходят с frontend; где партнёрские данные недоступны, демонстрационный режим явно виден.
- Команды запуска и теста записаны в README; `env.example` не содержит значений. В Git нет секретов и реальных клиентских данных.
- Backend запускается с чистого клона и даёт понятные ошибки при недоступности live API/модели.
- Коммиты backend отражают личный вклад Нурали, ветка объединена с общей до сдачи.
